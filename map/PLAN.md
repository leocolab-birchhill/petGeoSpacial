# Pet Valu Whitespace Map — Master Implementation Plan

This is the single source of truth for building the map app. The builder should follow
it top to bottom. Schemas referenced here are pinned in `DATA_CONTRACT.md`.

---

## 0. Hard constraints (non-negotiable)

- **NO new Mapbox API calls.** The routing cache in
  `../data/runtime/mapbox_matrix_cache/` (46,085 JSONs today) is the only routing
  source. No Mapbox token in the app, no Directions/Matrix/Isochrone calls, no Mapbox
  basemap. The cache contains **metrics only** (duration/distance) — no route
  polylines — so route display is **origin→store straight lines labelled with real
  driving metrics** (the user explicitly approved this fallback).
- **~14.6% of routing cache is still in flight** (7,874 of 53,959 R8 hexes missing;
  Databricks job running). Everything must tolerate missing routing: those hexes get
  `routing_status="pending"`, render normally for demand metrics, and render
  grey/hatched for access-derived metrics and classification. The whole pipeline is
  idempotent — re-run steps 01→03→04→05 when new cache lands.
- **Never ship raw national data as one browser GeoJSON.** 53,959 R8 polygons and
  762k postal points go to **PMTiles**. Only small layers (1,687 store points,
  ~hundreds of cluster outlines) load as plain GeoJSON.

## 1. Tech stack (decided)

| Concern | Choice | Rationale |
|---|---|---|
| App | React 18 + TypeScript + Vite | per spec |
| Map engine | **MapLibre GL JS v4** (+ `pmtiles` npm protocol) | vector tiles, expression-driven recolour/filtering, no keys |
| Big layers | PMTiles generated by **tippecanoe ≥ 2.17** (writes `.pmtiles` directly; run in WSL or Docker `felt/tippecanoe`) | single-file tile archives, HTTP range requests, no tile server |
| deck.gl | **Not used in v1.** MapLibre handles everything here (54k hex polygons in tiles, 1.7k stores, 3 selection lines). Revisit only if postal points-in-tiles feel heavy → deck.gl `ScatterplotLayer` behind a flag. Listed so the builder doesn't add it reflexively. |
| Basemap | **OpenFreeMap Positron** (`https://tiles.openfreemap.org/styles/positron`) — free, no key, light grey (ideal under choropleth). Fallback: CARTO Positron raster. | zero keys, satisfies "no Mapbox" |
| Pipeline | Python (pandas/polars + `h3` v4 + `shapely`), matching existing repo deps | reuse existing conventions |
| Serving | Vite dev server; prod = any static server with HTTP Range support (`npx http-server dist`). **No PostGIS, no tile server.** | PMTiles needs only range requests |

Windows note: tippecanoe is Linux-only. `05_make_tiles.sh` provides both WSL and
Docker invocations. Everything else runs on Windows Python/Node.

## 2. Data flow

```
../data/runtime/mapbox_matrix_cache/*.json  ─┐
../data/processed/h3_store_routing_input.parquet ─┴→ 01_assemble_routing.py
      → pipeline/build/h3_routing_wide.parquet   (53,959 rows; pending hexes flagged)

../data/raw/PET_data_stores...xlsx [Canadian Competitors, header row 15] → 02_build_competitors.py
      → pipeline/build/competitor_stores.parquet (817 rows, all geocoded, all Open)
      → pipeline/build/h3_competition.parquet    (per-R8-hex competitor intensity)

../data/processed/h3_r8_demographic_demand_ranking.parquet (58 cols, the demand model)
  + h3_routing_wide + h3_competition → 03_build_opportunity_scores.py
      → pipeline/build/h3_master.parquet         (one row per R8 hex: everything)
      → pipeline/build/h3_r7_rollup.parquet      (household-weighted rollup for low zoom)
      → pipeline/build/clusters.parquet          (contiguous high-opportunity clusters)

03 outputs + ../data/processed/pet_valu_network_stores.parquet
  + ../data/processed/postal_code_h3_crosswalk.parquet → 04_export_geojson.py
      → build/geojson/h3_r8.geojson.nd, h3_r7.geojson.nd, postal_points.geojson.nd  (tiling only)
      → app/public/data/stores.geojson            (870 network + 817 competitors, typed)
      → app/public/data/clusters.geojson          (outlines + aggregate stats)
      → app/public/data/details/{h3_id[:5]}.json  (sharded full detail records)
      → app/public/data/meta.json                 (metric domains, generated_at, coverage %)

05_make_tiles.sh (tippecanoe) →
      app/public/tiles/hexes.pmtiles   (layers: h3_r7 z3–7, h3_r8 z6–14)
      app/public/tiles/postal.pmtiles  (layer: postal z11–14)
```

Key decision — **tiles carry only paint/filter attributes** (~15 fields, see
DATA_CONTRACT §5); the click-time detail panel fetches the hex's full record from a
sharded JSON (`details/{first 5 chars of h3_id}.json`, ~1,300 shards of ~40 rows).
This keeps hex tiles small while the panel can show all demographics/data-quality
fields without a backend.

## 3. Derived analytics (computed in step 03)

### 3.1 Access metrics (from routing wide)
- `nearest_pv_minutes`, `nearest_pv_km`, `nearest_pv_store_id` — min over the 3
  cached destinations by driving time (nulls excluded).
- `avg3_pv_minutes` — mean driving minutes over non-null routes.
- `routing_status`: `ok` (≥1 non-null route) | `no_route` (cached, all null — Arctic
  etc.) | `pending` (no cache file yet).

### 3.2 Competitor intensity (straight-line only — no API calls)
Per R8 hex centroid (`hh_weighted_lat/lon` from ranking table):
- `competitors_within_5km`, `competitors_within_10km` (haversine, BallTree —
  reuse the `prepare_routing_inputs.py` pattern).
- `competitor_intensity` = gravity-style score `Σ 1/(1+d_km)` over competitors
  within 15 km, so a next-door PetSmart outweighs three distant independents.
- `nearest_competitor_km`, `nearest_competitor_chain`, `nearest_competitor_type`.
- `competitor_intensity_pct` — national percentile.

### 3.3 Competitor type classification (fixed mapping in `pipeline/config.py`)
From the 17 chains actually present (all-store counts verified):

| type | chains |
|---|---|
| `mass_merchant` | PetSmart (165), Petland (40) |
| `specialty_chain` | Global Pet Foods (220), Mondou (92), Ren's Pets (61), Pattes et Griffes (51), Pet Planet (45), Homes Alive Pets (9), Pet Depot (2), EarthWise Pet Supply (2) |
| `independent_boutique` | The Bone & Biscuit Co. (64), Woof Gang Bakery & Grooming (8), Three Dog Bakery (2) |
| `services_other` | VetCor (25), Dogtopia (8), Wild Birds Unlimited (22), Camp Bow Wow (1) — shown but **excluded from `competitor_intensity` by default** (weight 0.25, configurable) since they aren't primarily food/supply retail |

The known gap that ChainXY under-covers true independents goes in the map's data
notes ("competition may be understated").

### 3.4 Opportunity score (0–100)
```
opportunity_score = 100 * ( W_DEMAND      * national_demand_percentile
                          + W_ACCESS      * access_gap_pct        # pct-rank of nearest_pv_minutes (farther = higher)
                          + W_COMPETITION * (1 - competitor_intensity_pct) )
weights (config.py): W_DEMAND=0.5, W_ACCESS=0.3, W_COMPETITION=0.2
```
`opportunity_score = null` when `routing_status != ok` (rendered hatched). Weights
and thresholds live in `config.py` AND are exported into `meta.json` so the UI can
display "how this score is computed".

### 3.5 Market classification (explicit, per user spec)
Thresholds in `config.py` (defaults below; tune after first render):
- high demand: `national_demand_percentile ≥ 0.70`
- poor PV access: `nearest_pv_minutes ≥ 15` (urban hexes) / `≥ 25` (rural hexes)
- meaningful competition: `competitor_intensity_pct ≥ 0.60`

| class | demand | PV access | competition | colour |
|---|---|---|---|---|
| `true_whitespace` | high | poor | low | `#2e7d32` green |
| `proven_market_no_pv` | high | poor | meaningful | `#1565c0` blue |
| `competitive_infill` | high | good | high | `#ef6c00` orange |
| `weak_whitespace` | low | poor | low | `#9e9e9e` grey |
| `other` | everything else | | | `#e0e0e0` pale |
| `pending_routing` | — | unknown | — | hatched |

### 3.6 Contiguous high-opportunity clusters
- Members: hexes with `class ∈ {true_whitespace, proven_market_no_pv}` OR
  `opportunity_score ≥ 80`.
- Connected components over H3 adjacency (`h3.grid_ring(cell,1)` neighbours),
  keep components with ≥ 3 hexes.
- Per cluster: id, hex count, Σ addressable demand, mean opportunity, dominant
  class, largest city/province (mode of hex province + nearest network store city),
  bounding box. Geometry = dissolved outer boundary
  (`h3.cells_to_geo` multipolygon → shapely `unary_union` boundary).
- Output is small (expect low hundreds) → plain `clusters.geojson` + ranked list
  in the UI.

### 3.7 R7 rollup (low-zoom layer)
Household-weighted means of score/metrics from child R8 hexes; same field names.
Prevents rendering 54k polygons at national zoom.

## 4. Tiling (exact commands in `05_make_tiles.sh`)

```bash
# hexes.pmtiles — two layers, one archive
tippecanoe -o app/public/tiles/hexes.pmtiles --force \
  -L'{"file":"build/geojson/h3_r7.geojson.nd","layer":"h3_r7","minzoom":3,"maxzoom":7}' \
  -L'{"file":"build/geojson/h3_r8.geojson.nd","layer":"h3_r8","minzoom":6,"maxzoom":13}' \
  --detect-shared-borders --coalesce-fraction-as-needed --no-simplification-of-shared-nodes \
  --no-tile-size-limit-checking-at-max-zoom --read-parallel -P

# postal.pmtiles — points, high zoom only
tippecanoe -o app/public/tiles/postal.pmtiles --force \
  -l postal --minzoom=11 --maxzoom=14 -r1 --cluster-distance=0 --read-parallel -P \
  build/geojson/postal_points.geojson.nd
```
Write GeoJSON as newline-delimited (`.geojson.nd`) so tippecanoe streams with `-P`.
Docker alternative: `docker run --rm -v "$(pwd)":/data felt/tippecanoe:latest tippecanoe ...`.

## 5. App behaviour spec

### 5.1 Layout (CSS grid, no UI framework needed; plain CSS modules)
```
┌──────────────── TopBar: search (FSA/city/store) · province select · metric select ────────────────┐
│ FilterSidebar │                    MapView                        │ DetailPanel (slides in)        │
│  (left, coll- │   MapLibre canvas                                 │  hex/cluster detail            │
│   apsible)    │                                                   │                                │
├──────────────── BottomBar: legend (dynamic per metric) + classification key + coverage note ──────┤
```

### 5.2 Layers & zoom policy
| layer | source | visible | notes |
|---|---|---|---|
| basemap | OpenFreeMap positron | always | |
| `h3_r7` fill | hexes.pmtiles | z < 6.5 | same paint expression as r8 |
| `h3_r8` fill + subtle line | hexes.pmtiles | z ≥ 6.5 | the workhorse |
| pending-routing hatch | same tiles, `fill-pattern`, filter `routing_status != "ok"` | with hexes | only when metric is access/score/class |
| cluster outlines | clusters.geojson | always (thick line, no fill) | toggleable |
| stores | stores.geojson, MapLibre `cluster:true` | clustered z<9, individual z≥9 | icons: Pet Valu network = filled paw/circle by banner; competitors = distinct shapes/colours by `competitor_type` (mass=square, specialty=triangle, independent=diamond, services=cross) |
| postal points | postal.pmtiles | z ≥ 11 | tiny circles, radius by households, toggle default-off |
| selection: hex highlight | feature-state | on click | bold outline + glow |
| selection: 3 route lines | in-memory GeoJSON source | on click | origin→store straight lines, dashed; width by rank; labels "1 · 14.2 min · 11.3 km" |

### 5.3 Hex click → DetailPanel
1. `queryRenderedFeatures` → `h3_id`; set feature-state selected.
2. Fetch `details/{h3_id.slice(0,5)}.json`, pick record.
3. Panel sections: header (class chip, opportunity score dial, province,
   urban/rural) · **Routes** (3 rows: rank by driving time, store name/banner,
   driving minutes, driving km — straight-line rank shown as secondary if it
   differs; "routing pending" state when applicable) · Demand (addressable demand,
   percentiles, factor breakdown bars: income/housing/family/age) · Competition
   (intensity, nearest competitor + chain, counts within 5/10 km) · Demographics
   (households, population, median income, shares) · Data quality (flags,
   contributing postal codes, coordinate precision).
4. Route lines drawn simultaneously (see 5.2). Cluster click → same panel with
   cluster aggregate + "zoom to cluster" + member-hex ranked list.

### 5.4 Metric recolour (TopBar select) — all expression-driven, no data reload
`opportunity_score` (default) · `adjusted_addressable_demand` · `nearest_pv_minutes`
· `avg3_pv_minutes` · `competitor_intensity` · `market_class` (categorical).
Colour ramps + domain breaks come from `meta.json` (pipeline computes p5–p95
quantile breaks per metric). Legend updates accordingly.

### 5.5 Filters (left sidebar) — combined into one MapLibre `setFilter` expression
Range sliders: demand percentile, nearest-PV drive time, competitor intensity,
opportunity score. Checkbox groups: province, urban/rural, market class, routing
status. Layer toggles: clusters, network stores, competitors (by type), postal
points. A "reset" button; active-filter count badge.

### 5.6 Search (TopBar)
No geocoding API. Build `fsa_index.json` in step 04: FSA → centroid (from postal
crosswalk) plus store names/cities from stores.geojson. Client-side fuzzy match
(simple prefix/includes; 1.6k FSAs + 1.7k stores) → `map.flyTo`.

### 5.7 URL state
Encode viewport + metric + filters in `location.hash` for shareable views
(serialize on `moveend`/filter change, restore on load).

### 5.8 Performance requirements
Filtering/recolour must be pure MapLibre expressions (no source reload). All big
sources are tiled with zoom windows. `details/` fetches are per-click (~40-row
shards, cached in memory). Target: smooth pan at national zoom on integrated
graphics.

## 7. Ideas beyond the spec (recommended, in priority order)

1. **Whitespace spotlight mode** — one toggle that dims all hexes except
   `true_whitespace`/`proven_market_no_pv` and pulls cluster outlines forward.
   Cheapest high-impact way to "convey whitespace". (build in v1)
2. **Ranked cluster list panel** — top clusters by Σ addressable demand with
   fly-to; turns the map into an actionable target list. (v1)
3. **Bivariate demand × access choropleth** — 3×3 two-colour grid, the classic
   whitespace visual; legend as a small matrix. (v1.5, expressions already support it)
4. **Legend histogram with brush** — distribution of the active metric; brushing
   filters the map. (v1.5)
5. **Data-confidence overlay** — hatch hexes with `flag_income_imputed` or
   `coordinate_precision_flag='rural_fsa_centroid_imprecise'`; honest-map mode for
   exec review. (v1.5)
6. **Straight-line service rings** around a clicked store (5/10/15 km circles,
   client-side turf) — approximates isochrones without any API. (v2)
7. **CSV export of filtered hexes** from current filter state. (v2)
8. **Coverage banner** — "routing 85.4% complete" from `meta.json`, so viewers know
   grey hatching = pending Databricks job, not missing data. (v1, trivial)

Explicitly rejected: live isochrone APIs (violates no-API rule), PostGIS (static
files suffice), server-side tile server (PMTiles range requests suffice), deck.gl in
v1 (adds a second renderer for no current need).

## 8. Build phases (for the implementing model)

- **Phase 0 — pipeline**: implement `01`→`04` per DATA_CONTRACT; unit-check row
  counts (53,959 master rows; 817 competitors; 870 network stores). Log coverage %.
- **Phase 1 — tiles + shell**: run `05`; scaffold app; basemap + h3_r8 choropleth
  (opportunity score) + zoom handoff to r7; stores layer with clustering.
- **Phase 2 — interaction**: click → highlight + DetailPanel + 3 route lines;
  hover tooltip.
- **Phase 3 — controls**: metric recolour, filters, search, legend, URL state.
- **Phase 4 — analytics polish**: classification view, cluster outlines + ranked
  list, spotlight mode, coverage banner, pending-routing hatching.
- **Phase 5 — re-run drill**: when remaining cache lands, re-run 01/03/04/05 and
  verify pending count drops; no code changes should be needed.
